ТЕХНИЧЕСКОЕ ЗАДАНИЕ
База данных сервиса пробных экзаменов
Версия 1.0

Цель: реализовать минималистичную, расширяемую модель данных для сервиса пробных экзаменов, работающего локально и на VPS на одной и той же SQLite-базе.
1. Общие требования
•	База должна одинаково использоваться локальной версией приложения и серверной версией на VPS.
•	Основной формат хранения — SQLite, один файл data/probnik.db.
•	Архитектура должна допускать последующий переход на PostgreSQL без изменения бизнес-модели.
•	Импорт из CRM не должен быть жёстко связан со схемой базы: Excel обрабатывается отдельным импортёром.
•	Никакой повторный импорт не должен удалять историю ученика, старые группы или результаты экзаменов.
•	Физическое удаление учеников и исторических данных не использовать; применять статусы активности и даты завершения связей.
Основные сущности:
Student
Staff
StudyGroup
Membership
Exam
Participation
Связи: Student ↔ Membership ↔ StudyGroup; Staff → StudyGroup; Student ↔ Participation ↔ Exam.
2. Таблица students
Хранит ученика независимо от того, занимается он сейчас или находится в архиве.
Поле	Тип	Обяз.	Назначение
id	INTEGER PK	Да	Внутренний ID
external_id	TEXT NULL	Нет	ID ученика из CRM, если появится
full_name	TEXT	Да	ФИО ученика
name_key	TEXT	Да	Нормализованное ФИО для поиска и текущей синхронизации
grade	INTEGER NULL	Нет	Класс обучения
is_active	BOOLEAN	Да	Активен ли ученик сейчас
access_code_hash	TEXT NULL	Нет	Хеш кода доступа ученика

Пример нормализации:
"  ИВАНОВ   Алексей Петрович " → "иванов алексей петрович"
Важно: external_id предусмотреть сразу. Пока CRM не отдаёт постоянный ID, ученика можно сопоставлять по name_key. При появлении ID синхронизацию перевести на external_id.
3. Таблица staff
Одна таблица для преподавателей, ответственных и администраторов.
Поле	Тип	Обяз.	Назначение
id	INTEGER PK	Да	ID сотрудника
name	TEXT	Да	ФИО/имя
login	TEXT UNIQUE	Да	Логин
password_hash	TEXT	Да	Хеш пароля
role	TEXT	Да	Роль пользователя

Допустимые роли:
admin
responsible
teacher
Отдельные таблицы teachers, admins и responsibles не создавать.
4. Таблица study_groups
Хранит группы из CRM и их нормализованные свойства.
Поле	Тип	Обяз.	Назначение
id	INTEGER PK	Да	ID
source_name	TEXT	Да	Исходное название группы из CRM
subject	TEXT NULL	Нет	Предмет
teacher_id	INTEGER FK NULL	Нет	Преподаватель
is_active	BOOLEAN	Да	Группа используется сейчас

Пример:
source_name = "Русский язык ОГЭ 2гр. ВТ и ЧТ 15:00 Алина"
subject = "Русский язык"
teacher_id = 12
На первом этапе subject и teacher_id могут быть NULL, если текущую строку CRM нельзя надёжно разобрать. source_name сохранять обязательно.
5. Таблица memberships
Хранит связь ученика с группой и полную историю входа/выхода из групп.
Поле	Тип	Обяз.	Назначение
id	INTEGER PK	Да	ID
student_id	INTEGER FK	Да	Ученик
group_id	INTEGER FK	Да	Группа
started_at	DATE	Да	Дата появления в группе
ended_at	DATE NULL	Нет	Дата выхода из группы

Активная связь: ended_at = NULL
Архивная связь: ended_at != NULL
Если ученик вернулся в ту же группу, старая запись не изменяется: создаётся новая membership. Отдельная таблица архива не нужна.
6. Таблица exams
Одна таблица используется и для пробников, и для реального ЕГЭ.
Поле	Тип	Обяз.	Назначение
id	INTEGER PK	Да	ID
type	TEXT	Да	mock или ege
subject	TEXT	Да	Предмет
title	TEXT NULL	Нет	Отображаемое название
wave	TEXT NULL	Нет	Период/волна, например 2026-10
starts_at	DATETIME	Да	Начало экзамена
ends_at	DATETIME NULL	Нет	Окончание
registration_open_at	DATETIME NULL	Нет	Начало записи
registration_close_at	DATETIME NULL	Нет	Конец записи
structure_data	JSON NULL	Нет	Структура заданий экзамена
is_active	BOOLEAN	Да	Активен ли экзамен

Если один предмет проводится в разные дни, каждая дата является отдельной записью Exam.
7. JSON Exam.structure_data
JSON описывает структуру заданий конкретного экзамена. Формат версии 1:
{
  "version": 1,
  "tasks": [
    {"code": "1",  "title": "Задание 1",  "max_score": 1},
    {"code": "2",  "title": "Задание 2",  "max_score": 1},
    {"code": "26", "title": "Задание 26", "max_score": 2}
  ]
}
Поле code хранить строкой. Это позволит использовать значения 1, 26, 27.1, К1, К2 и другие без изменения БД.
8. Таблица participations
Главная таблица экзамена. Одна запись одновременно представляет запись ученика, явку, сдачу работы, проверку, результат и публикацию.
Поле	Тип	Обяз.	Назначение
id	INTEGER PK	Да	ID
student_id	INTEGER FK	Да	Ученик
exam_id	INTEGER FK	Да	Экзамен
status	TEXT	Да	Текущее состояние участия
primary_score	REAL NULL	Нет	Первичный балл
test_score	REAL NULL	Нет	Тестовый/итоговый балл
result_data	JSON NULL	Нет	Подробный результат
updated_at	DATETIME	Да	Последнее изменение
published_at	DATETIME NULL	Нет	Время публикации

Обязательное ограничение:
UNIQUE(student_id, exam_id)
9. Статусы участия
registered → attended → submitted → checked → published
Статус	Значение
registered	Ученик записался
attended	Ученик пришёл
submitted	Ученик сдал работу
checked	Работа проверена
published	Результат опубликован
absent	Ученик не пришёл
cancelled	Запись отменена

Не создавать отдельные поля is_registered, is_attended, is_submitted, is_checked. Поле status является единственным источником текущего состояния.
10. JSON Participation.result_data
Подробные результаты ученика хранятся одним JSON-объектом.
{
  "version": 1,
  "tasks": [
    {"code": "1",  "score": 1, "comment": ""},
    {"code": "2",  "score": 0, "comment": "Ошибка при переводе числа"},
    {"code": "26", "score": 2, "comment": "Верное решение"}
  ],
  "overall_comment": "Хороший результат. Нужно повторить системы счисления."
}
Максимальный балл задания берётся из Exam.structure_data и не дублируется в result_data без необходимости.
Итоговые баллы хранить отдельно: primary_score и test_score должны оставаться обычными колонками, чтобы быстро считать средний балл, динамику, сравнение групп и пробник → ЕГЭ.
11. Импорт из CRM
Формат Excel не должен быть связан напрямую с моделью БД.
Excel CRM → ExcelImporter → нормализованные данные → SyncService → Database
•	Текущий Excel используется только как источник данных для разработки.
•	Импортёр должен читать текущие поля: ФИО, статус обучения, активные группы, класс обучения.
•	Если формат выгрузки CRM изменится, заменяется только импортёр; схема базы и бизнес-логика остаются прежними.
12. Повторный импорт и синхронизация
При новой загрузке Excel база не очищается. Система сравнивает новую выгрузку с текущим состоянием.
•	Определить учеников без изменений.
•	Определить новых учеников.
•	Определить вернувшихся учеников.
•	Определить учеников, исчезнувших из новой выгрузки.
•	Определить новые группы.
•	Определить добавленные связи ученика с группой.
•	Определить удалённые связи ученика с группой.
Пример предварительного отчёта:
В файле: 329
Без изменений: 301
Новых: 12
Вернувшихся: 3
Ушли: 8
Сменили группы: 5
Новых групп: 2
Изменения применяются только после подтверждения пользователя.
13. Правила синхронизации
13.1 Новый ученик
•	Создать Student с is_active = true.
•	Создать необходимые StudyGroup и Membership.
13.2 Ученик остался
•	Обновить ФИО и класс при необходимости.
•	Установить is_active = true.
•	Результаты экзаменов не изменять.
13.3 Ученик исчез из новой выгрузки
•	Не удалять Student.
•	Установить is_active = false.
•	Закрыть все активные Membership: ended_at = текущая дата.
13.4 Ученик вернулся
•	Использовать существующий Student, не создавать новый.
•	Установить is_active = true.
•	Создать новые Membership при необходимости.
•	Все прошлые Participation остаются связанными с тем же student_id.
13.5 Ученик ушёл из одной группы
•	Закрыть только соответствующую Membership.
•	Сам Student остаётся активным, если присутствует в новой выгрузке.
13.6 Ученик перешёл в другую группу
•	Старую Membership закрыть.
•	Создать новую Membership с started_at = текущая дата.
•	Историю не перезаписывать.
14. История результатов и реальный ЕГЭ
Participation связывается напрямую с student_id и exam_id. Результат никогда не должен зависеть от текущей группы ученика.
Иванов Алексей / Информатика
Октябрь 2026  Пробник  61
Январь 2027   Пробник  72
Март 2027     Пробник  78
Июнь 2027     ЕГЭ      84
Для реального ЕГЭ отдельную таблицу не создавать: использовать Exam.type = "ege" и обычную Participation.
15. Индексы и ограничения
•	Индексы: students.name_key, students.external_id.
•	Индекс/уникальность: study_groups.source_name.
•	Индексы: memberships.student_id, memberships.group_id, memberships.ended_at.
•	Индексы: exams.subject, exams.starts_at, exams.type, exams.wave.
•	Индексы: participations.student_id, participations.exam_id, participations.status.
•	UNIQUE(student_id, exam_id) для participations.
•	Все внешние ключи должны быть включены и проверяться SQLite.
16. Требования к SQLite
PRAGMA foreign_keys = ON;
PRAGMA journal_mode = WAL;
Все операции синхронизации CRM выполнять в одной транзакции. При ошибке импорт не должен частично менять базу.
17. Резервное копирование
•	Приложение должно уметь создавать полную резервную копию базы.
•	При запущенном приложении backup выполнять через штатный SQLite Backup API, а не простым копированием открытого файла.
•	Копия должна без преобразований переноситься VPS → локальное приложение и обратно.
Пример:
backups/probnik_2026-11-15.db
backups/probnik_2027-02-01.db
18. Итоговая модель
Сущность	Основные поля

19. Критерии готовности
1.	Создать пустую SQLite-базу.
2.	Загрузить текущий Excel CRM и получить учеников и группы.
3.	Повторно загрузить изменённый Excel и корректно определить: новый / ушёл / вернулся / сменил группу.
4.	Создать пробный экзамен.
5.	Записать ученика и пройти статусы registered → attended → submitted → checked → published.
6.	Сохранить первичный и тестовый балл.
7.	Сохранить балл и комментарий по каждому заданию и общий комментарий.
8.	Архивировать ученика повторным импортом.
9.	Вернуть ученика новым импортом и убедиться, что старый результат сохранился.
10.	Добавить результат реального ЕГЭ без создания новых таблиц.
11.	Создать backup БД.
12.	Открыть этот backup локальной версией приложения.
Ключевой принцип
Модель хранит постоянную историю ученика, а текущая CRM используется только как источник актуального состояния. Ни один импорт не должен удалять старые результаты или историю обучения.
